# Ветки, ревью и релизы

## Ветки и pull request

| Ветка                                  | Откуда начать                          | Куда передавать изменения                                                                                      |
| -------------------------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `main`                                 | Постоянная ветка истории выпусков      | Принимает выпуск из `staging` или исправление из `hotfix/*`.                                                   |
| `develop`                              | Постоянная ветка интеграции            | Принимает рабочие PR и обратный перенос релизных исправлений.                                                  |
| `staging`                              | Постоянная ветка предрелизной проверки | Принимает одну активную `release/*`, затем передаёт проверенную версию в `main`.                               |
| `feat/*`, `fix/*`, `chore/*`, `docs/*` | Актуальная `develop`                   | PR в `develop` через squash merge. Для корректировки кандидата `fix/*` можно направить в активную `release/*`. |
| `release/X.Y.Z`                        | Выбранный коммит `develop`             | PR в `staging` через merge commit. Исправления возвращаются в `develop` через PR из релизной ветки.            |
| `hotfix/*`                             | Тег версии, работающей в production    | PR в `main` через merge commit. Затем исправление возвращается в ветки активной разработки.                    |

Создавай временную ветку под фактическую задачу. Если есть карточка, включай её идентификатор в имя, например `feat/APP-42-telegram-profile`. Веди независимые задачи в отдельных ветках или worktrees. У каждой ветки есть один ответственный за её изменения. Для совместной правки согласуй владельцев файлов и очередь обновлений.

Когда есть осмысленный diff, отправь рабочую ветку на сервер и открой Draft PR, если нужна совместная работа, ранний отзыв или CI. В PR укажи задачу, критерии, затронутые сценарии и открытые вопросы. Перед Ready for review добавь фактические результаты проверок. После squash заголовок коммита должен следовать Conventional Commits. После закрытия связанных PR временную ветку можно удалить.

## Когда запускать проверки и ревью

| Момент              | Действие                                                                                                                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| До реализации       | Техлид проверяет план при изменении API, схемы данных, границ сервисов или выкладки. AppSec участвует при изменении авторизации или границ доверия. Database проверяет рискованные миграции. |
| Перед коммитом      | Автор читает staged diff. Lefthook проверяет staged diff на проблемы с пробелами, запускает линтер и проверку формата. Commitlint проверяет сообщение. После коммита Engram обновляет граф.  |
| Перед push          | Lefthook выполняет `npm run check`. Автор проверяет целевую ветку PR и актуальность ожидаемого контракта.                                                                                    |
| На Draft PR         | Зови ревьюера раньше, если нужно решение по конкретному спорному вопросу.                                                                                                                    |
| На Ready for review | Независимый `reviewer` проверяет актуальный diff относительно целевой ветки и фиксирует head SHA. QA подтверждает критерии меняющегося поведения.                                            |
| После изменений     | Перезапусти затронутые проверки. При существенном изменении поведения, контракта, миграций или доступа запроси повторное ревью нового diff.                                                  |
| Перед merge         | Сверь head SHA, зелёный CI и статус блокирующих замечаний. Для релиза также проверь подтверждение владельца и результаты staging.                                                            |

GitHub Actions проверяет маршрут PR, сообщения коммитов, `npm run check` и Playwright. Ревью запускает человек или ведущая сессия в отдельной роли. Механические проверки Lefthook выполняются локально. При работе без GitHub зафиксируй результат независимого ревью с идентификатором коммита.

## Релиз

1. Release Manager выбирает состав из `develop`, фиксирует кандидата и создаёт `release/X.Y.Z`. Кандидат принимает только нужные для выпуска исправления. Создавай их ветки `fix/*` от активной `release/X.Y.Z` и направляй PR обратно в неё. Команда продолжает обычную работу в `develop`.
2. После ревью и зелёного CI влей кандидата в `staging` через merge commit. Сверь дерево коммита в `staging` с выбранным `release/X.Y.Z`. Если там остались изменения отменённого кандидата, сначала убери их обычным PR с откатом через релизную ветку. На staging проверь сборку из этого коммита, `/api/health/ready` и затронутые сценарии. Для изменений Telegram WebView проверь реальный клиент, если релиз зависит от его поведения. Зафиксируй SHA кандидата, идентификатор или digest артефакта и результаты.
3. Подготовь PR `staging` → `main`. Проверь ревью релиза, миграции, совместимость новой схемы с предыдущим приложением и условия отката. Если `main` изменился после подготовки кандидата, синхронизируй `main` → `release/X.Y.Z`, затем `release/X.Y.Z` → `staging` и повторно проверь кандидата. После явного подтверждения владельца влей PR через merge commit. Сверь итоговое дерево `main` с проверенным кандидатом. При расхождении верни итоговый состав на проверку и получи подтверждение на него.
4. На коммите выпуска создай тег `vX.Y.Z` и продвинь уже проверенный артефакт в production. Проверь readiness, ключевой сценарий и ошибки Observe. Если деплой требует отката, используй согласованный предыдущий артефакт и план работы со схемой.
5. Верни исправления релиза в `develop` через PR из `release/X.Y.Z`. В отчёте укажи тег, артефакт, фактический результат и открытые риски. Для задачи с критерием выкладки статус после merge рабочего PR — «Готово к релизу», после успешной проверки на production — «Готово».

### Hotfix

Создай `hotfix/*` от тега текущего production и проверь ровно этот состав. При занятом staging используй согласованное тестовое окружение для hotfix, чтобы сохранить текущего кандидата. До merge сравни дерево `main` с текущим production-тегом. Если в `main` есть ещё не выложенные изменения, согласуй с владельцем состав patch-релиза и точный коммит для тега. Выпускай артефакт из проверенного состава после независимого ревью и решения владельца. После выпуска синхронизируй исправление через PR `main` → `develop`. При активном релизе также выполни `main` → `release/X.Y.Z` через merge commit, обнови `staging` из релизной ветки и повторно проверь кандидата.

## Подключение GitHub

После создания удалённого репозитория укажи его URL как `origin`. Сначала опубликуй `main` и назначь её веткой по умолчанию, затем опубликуй `develop` и `staging`. Дождись первого прогона `Check / check` перед настройкой rulesets. Этот шаблон задаёт проверки и процесс выпуска. Окружения, артефакты и выкладку настраивают для выбранного хостинга.

Для `main`, `develop`, `staging` и веток `release/*` настрой ruleset с обязательным PR, обязательной проверкой `Check / check` и завершением обсуждений. Выбери job `check` из списка после первого запуска workflow `Check`. Для релизных веток сохрани возможность создавать новые кандидаты. Запрети force-push на защищённых ветках и удаление постоянных веток. После обратного переноса исправлений временную `release/*` можно удалить. Если есть человек с правом независимого ревью, настрой обязательный approval и сброс устаревшего approval после новых коммитов. Иначе владелец принимает решение по результату независимой проверки diff. Оставь доступными squash и merge commit для соответствующих маршрутов. Для `staging` → `main` достаточно обязательного прогона на merge-результате. Если дополнительно включена проверка, что ветка PR содержит актуальный `main`, синхронизируй `main` → `release/X.Y.Z` → `staging` перед проверкой кандидата.
