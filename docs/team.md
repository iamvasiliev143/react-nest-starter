# Команда разработки

Владелец проекта утверждает продуктовые приоритеты, принимает риски и принимает решение о выпуске. Основная сессия ведёт задачу как техлид. В Claude Code роли доступны как проектные субагенты. В остальных инструментах таблица задаёт зоны ответственности и порядок передачи работы.

| Роль                  | Когда подключать                                           | Ожидаемый результат                                          |
| --------------------- | ---------------------------------------------------------- | ------------------------------------------------------------ |
| `product-manager`     | Инициатива, приоритет или изменение объёма                 | Проблема, приоритет и критерий успеха                        |
| `project-manager`     | Работа нескольких ролей или зависимостей                   | План, владельцы, блокеры и статус                            |
| `business-analyst`    | Бизнес-правила или изменение процесса                      | Сценарии и критерии приёмки                                  |
| `ux-designer`         | Новый пользовательский поток                               | Поток, состояния интерфейса и требования доступности         |
| `tech-lead`           | Технический план и интеграция                              | Контракт, распределение задач и итоги проверок               |
| `architect`           | Решение, которое дорого пересматривать                     | Варианты, компромиссы и проект ADR                           |
| `frontend`            | Изменения в React                                          | Интерфейс, интеграция и проверки клиента                     |
| `backend`             | Изменения в NestJS                                         | API, серверная логика и проверки                             |
| `database`            | Данные, запросы или миграции                               | Схема, миграция и оценка риска                               |
| `platform`            | Окружение, сборка или доставка                             | Воспроизводимый запуск и конфигурация CI                     |
| `sre`                 | Надёжность и эксплуатация                                  | Метрики, сигналы, план восстановления                        |
| `qa`                  | Изменение поведения                                        | Результаты приёмки и воспроизводимые дефекты                 |
| `qa-automation`       | Сценарий для регулярной регрессии                          | Автоматические тесты и результат прогона                     |
| `performance`         | Риск задержек или потребления ресурсов                     | Бюджет, замеры и выводы                                      |
| `reviewer`            | Diff с изменением поведения                                | Независимые замечания и пробелы проверок                     |
| `appsec`              | Авторизация, границы доверия или чувствительные данные     | Модель угроз, защитные меры и замечания                      |
| `security-validation` | Требуется независимая проверка защиты                      | Оценка защитных тестов и доказательств, открытые пробелы     |
| `privacy`             | Персональные или регулируемые данные                       | Карта данных и замечания по доступу, логам и срокам хранения |
| `technical-writer`    | Меняются команды, контракты или пользовательское поведение | Проверенная документация                                     |
| `release-manager`     | Подготовка выпуска                                         | Статус готовности, блокеры и условия отката                  |

## Передача задачи

Перед запуском агента укажи цель, режим работы (план, реализация, проверка), доступные пути, критерии готовности и какие результаты ждёшь. Передай ссылку на актуальный контракт или diff, когда он нужен. Если ветка или worktree уже есть, укажи его. В ответ агент возвращает результат, фактические проверки, открытые вопросы и следующий шаг для принимающей роли.

- Фича через web и API. Техлид согласует контракт, затем `frontend` и `backend` могут работать параллельно. `qa` проверяет сценарий целиком, `reviewer` независимо проверяет итоговые изменения.
- Telegram-вход, разграничение доступа или чувствительные данные. `appsec` проверяет дизайн, `backend` реализует меры защиты, `qa-automation` добавляет регрессии, `security-validation` сверяет защитные требования и результаты. Для обработки персональных данных подключай `privacy`.
- Новая миграция. `database` оценивает совместимость и порядок применения. `platform` подключается при изменении среды или CI, `release-manager` проверяет условия выпуска и отката.
- Небольшая локальная правка. Ведущая сессия может выполнить её сама. Приглашай специалиста, если нужна отдельная компетенция или независимая проверка.

## Рабочий процесс

1. Согласуй цель, критерии готовности и ограничения. Продуктовые решения при необходимости выноси владельцу.
2. Определи затронутые модули. Для вопросов об архитектуре используй Engram и сверяй выводы с кодом. Перед параллельной работой согласуй контракт API и владельцев файлов. Независимые задачи можно вести в отдельных worktrees. Рабочие ветки начинаются от `develop`.
3. Передавай специалисту цель, границы файлов, критерии готовности и ожидаемый результат. Координируй работу последовательно, если исполнители зависят друг от друга или редактируют одни файлы.
4. После реализации выполни `npm run check`, передай актуальный diff PR на независимое ревью и проверь критерии приёмки. Для задач с границами доверия подключай `appsec` на этапе дизайна и `security-validation` к оценке защитных тестов после реализации.
5. Собери подтверждённые результаты, открытые риски и непроведённые проверки. При необходимости обнови документацию и передай владельцу готовность к выпуску.

Из корня проекта можно начать с `npm run ai:claude -- --agent tech-lead` или попросить обычную сессию Claude Code подключить нужную роль по имени. Роли `frontend` и `backend` получают глубину и границы работы из задачи. Архитектурные изменения и решения о совместимости координирует техлид.

Порядок ветвления, точки ревью и критерии передачи релиза описаны в [руководстве по Git и релизам](git-workflow.md).

## Задачи и отчётность в Notion

Если задача ведётся в Notion, ведущая сессия начинает с карточки и связанных решений. Project Manager ведёт статус и блокеры, Product Manager и Business Analyst уточняют требования и критерии. Technical Writer обновляет согласованную документацию, Release Manager собирает отчёт о выпуске. Техлид координирует итоговую запись, а специалисты передают ему проверенные факты. [Порядок работы и выбор записи](notion.md)

## Навыки по этапам

| Ситуация                                               | Навык                       | Кто применяет                                          |
| ------------------------------------------------------ | --------------------------- | ------------------------------------------------------ |
| Идея с размытыми требованиями                          | `feature-spec`              | product-manager, business-analyst, tech-lead           |
| Меняется HTTP-контракт                                 | `api-contract`              | tech-lead, backend, frontend                           |
| Меняется схема PostgreSQL                              | `db-migration`              | database, backend                                      |
| Меняется Telegram-вход или серверные права             | `telegram-auth-change`      | tech-lead, backend, appsec, security-validation        |
| Меняется тема, навигация или запуск в Telegram WebView | `telegram-mini-app-webview` | frontend, ux-designer, qa, qa-automation               |
| Нужны задачи, решения, документация или отчёт в Notion | `notion-workflow`           | ведущая сессия и владелец записи                       |
| Есть сценарий, который нужно подтвердить               | `behavior-test`             | frontend, backend, qa, qa-automation                   |
| Сбой с неясной причиной                                | `diagnose-bug`              | frontend, backend, platform, sre                       |
| Неизвестный поток или влияние между модулями           | `engram-context`            | tech-lead, разработчики, reviewer через краткую сводку |
| Создаём ветку, готовим push или PR                     | `git-workflow`              | tech-lead, исполнитель, reviewer                       |
| Готов diff для независимой проверки                    | `review-change`             | reviewer, appsec по границам доверия                   |
| Сдача изменений                                        | `verify`                    | tech-lead, исполнитель                                 |
| Готовим выпуск или передаём работу                     | `release-handoff`           | release-manager, technical-writer, project-manager     |

## Общие инженерные и UX-навыки

| Ситуация                                             | Навык                   | Кто применяет                               |
| ---------------------------------------------------- | ----------------------- | ------------------------------------------- |
| Меняются границы модулей, хранение или развёртывание | `architecture-decision` | tech-lead, architect, platform              |
| Нужно упростить код с сохранением поведения          | `refactor-safely`       | frontend, backend, reviewer                 |
| Появляется новый пользовательский сценарий           | `ux-flow`               | ux-designer, business-analyst, frontend, qa |
| Появляется новый или повторяемый UI-паттерн          | `ui-consistency`        | ux-designer, frontend                       |
| Меняется форма, навигация или интерактивный элемент  | `accessibility-review`  | ux-designer, frontend, qa                   |

Для сложного технического решения используй `architecture-decision` до реализации, затем подключай профильный навык по затронутому контракту, миграции или интеграции. Для нового интерфейса начни с `ux-flow`, добавь `ui-consistency` при проектировании паттерна и проверь доступность вместе с QA до сдачи.

## Навыки фреймворков

| Изменение                                                       | Навык                   | Кто применяет                 |
| --------------------------------------------------------------- | ----------------------- | ----------------------------- |
| Модуль NestJS, регистрация provider, DI, bootstrap или shutdown | `nestjs-practices`      | tech-lead, backend, reviewer  |
| Эффект React, подписка, таймер, зависимость или custom hook     | `react-hooks-practices` | tech-lead, frontend, reviewer |

Из корня проекта Claude Code ограничивает автоматическую загрузку этих навыков файлами из `api/src/` и `web/src/` соответственно, а описание уточняет тип изменения. При делегировании техлид указывает подходящий навык в поручении. Reviewer читает нужный раздел с текущими правами. В Codex выбор опирается на описания навыков и правила в `AGENTS.md`.

В Claude Code навыки лежат в `.claude/skills/` и вызываются как `/api-contract`. В Codex одноимённые навыки лежат в `.agents/skills/`, вызываются как `$api-contract` и открывают ту же инструкцию. Ведущая сессия указывает нужный навык или путь к нему в задании специалисту. Для обычной фичи достаточно постановки, проверки поведения и итоговой верификации. Остальные процедуры включаются по изменённым областям и рискам.
